# ROS 2 제어·통신 주기 기준

2026-11-05 측정 기준이다. 기존 Mega v8의 주행·제동 PID 보정값과 1000 Hz 계산 주기를 유지한다. 직접 위치 P를 추가하고 유지 출력을 강화한 펌웨어의 활성 실행시간은 아직 측정하지 않았다. 아래 ROS 값은 제안이며, 아직 ROS 모터 어댑터나 Nav2에 적용한 설정은 아니다. Nav2 주기는 SLAM 동시 실행 상태에서 20·30·50 Hz를 비교한 뒤 결정한다.

| 기능 | 현재 값 또는 검토 후보 | 상태·근거 |
| --- | --- | --- |
| Mega 속도 PID 계산 | 1000 Hz | 바퀴를 띄운 상태의 기존 구동 검증 유지 |
| 정지 위치 유지 | 같은 1000 Hz 루프 | 직접 위치 P + 속도 피드백; 목표 0 갱신이 끊기면 300 ms 명령 만료로 해제. 활성 실행시간 재측정 대기 |
| 엔코더 샘플링 | 20 kHz | 기존 검증 유지 |
| I²C 버스 | 기본 400 kHz | 기존 구동 검증 기준; 오류 시 100 kHz로 전환 |
| 모터드라이버 출력 갱신 | 기존 스케줄러 유지 | 이전 주행 실측 평균 약 580 Hz. PID 계산 주기와 다름 |
| 호스트 → Mega 목표속도 | 50 Hz | 이전 연속 주행 시험에서 실측 약 49.97 Hz |
| Mega → 호스트 상태 | 20 Hz | 실측 약 19.96–19.98 Hz |
| Nav2 로컬 주행 제어 | 20·30·50 Hz 비교 예정 | 미적용. 20 Hz는 최적값이나 고정 표준이 아님 |
| 속도 평활화·모터 어댑터 송신 | 50 Hz | 평활화를 사용하면 가감속 제한을 하위 제어와 일치시킴 |
| ROS 상위 명령 만료 | 200 ms 제안 | 수신 원본 명령의 시각을 확인. 오래된 목표를 재송신해 무기한 연장하지 않음 |
| MCU 목표 유효기간·watchdog | 300 ms | 기존 안전 한도 유지 |
| 운용 속도 상한 | 95 RPM | MCU 목표 상한·과속 감시 기준 100 RPM 유지 |

Jetson에서 SLAM, Nav2, 센서 처리, 바퀴 속도 변환과 오도메트리를 수행하고, Mega는 엔코더·속도 PID·정지 위치 유지·드라이버 출력·통신 감시를 담당한다. 오도메트리는 실제 엔코더 피드백을 사용한다. 20 Hz 데이터를 50 Hz로 다시 발행해도 새 측정이 늘어나는 것은 아니다. 측정 시각을 보존하고, 더 빠른 피드백이 필요하면 UART 대역폭과 실제 주행을 다시 측정한다.

## 무구동 통신 비교

실행: `python3 tools/profile_motor_link.py`. 이 도구는 전용 v8 펌웨어 식별 후 STOP/PING만 허용하며, 각 주기를 기본 8초씩 검사한다. 조종 프로그램을 종료한 상태에서 실행한다.

결과: 로컬 측정 보고서 `reports/motor_link_profile_20261105_165245_819142/summary.json`.

| 요청 주기 | 실제 송신 | 응답 왕복 p95 | MCU→호스트 UART 사용률 | 오류·타이머 누락 |
| --- | --- | --- | --- | --- |
| 20 Hz | 19.82 Hz | 12.39 ms | 23.79% | 0 |
| 50 Hz | 48.72 Hz | 13.71 ms | 31.56% | 0 |
| 100 Hz | 93.09 Hz | 12.27 ms | 43.13% | 0 |

응답을 기다린 후 다음 명령을 보내는 PING 검사다. Python 스케줄링과 응답 대기 때문에 요청 주기보다 실제 송신이 느리며, 이것을 MCU의 최대 처리 주파수로 해석하지 않는다. PING은 실제 목표속도 명령보다 짧다. UART 사용률은 115200 bps, 8N1의 방향별 전송량으로 계산했고 송수신 비율을 더하지 않는다. 응답 시간은 호스트 전송부터 ACK 수신까지이며 바퀴 반응 시간이 아니다. 각 단계 8초의 짧은 비교이므로 응답 지연의 작은 차이를 성능 우열로 단정하지 않는다.

모터 출력은 해제했고 PID 활성 업데이트는 0회다. 이 결과는 동작 중 PID 부하나 SLAM 동시 실행 성능을 검증한 것이 아니다. 주행 근거는 로컬 보고서 `reports/pid_recalibration_v8_20261105_124619/summary.json` 및 [motor_pid.json](../config/motor_pid.json)을 사용한다.

## Nav2 주기 결정

Nav2의 주파수는 여기서 로컬 경로 추종 제어기의 명령 생성 주기를 뜻한다. 전역 경로 계획, costmap, SLAM, 모터 PID가 모두 같은 주기로 실행되는 것은 아니다. Nav2 20 Hz에서도 Mega는 목표 사이에 1000 Hz로 바퀴 속도를 보정한다.

공식 MPPI 문서는 30 Hz 예시와 계산량을 조절한 50 Hz 운용을 설명한다. 빠른 주행과 곡선 추종에서 높은 주기가 유리할 수 있지만, 주기 내 계산 완료와 위치 정보의 최신성을 함께 확인해야 한다. 높은 송신 빈도만으로 새로운 측정이나 더 빠른 실제 출력이 보장되지는 않는다.

무구동 PING 비교는 통신 안정성 참고 자료다. 50 Hz가 실제 주행이나 Nav2의 최적값임을 입증하지 않는다. ROS 연동 후 PID는 1000 Hz로 고정하고 Nav2 20·30·50 Hz를 각각 비교한다. CPU 평균 부하뿐 아니라 지연 p95/p99, 주기 누락, 오도메트리 나이, 경로 추종 오차를 기록한다.

## PID 주기 변경 판단

기존 최대 실행시간 816µs는 위치 유지 비활성 상태에서 `micros()`로 잰 경과시간이며 중첩된 엔코더·UART·I²C 인터럽트 시간이 포함될 수 있다. 평균 CPU 사용률 81.6%를 뜻하지 않는다. 새 위치 유지 분기의 실행시간을 입증하는 수치도 아니다. 사용자 실기 시험에서 `HOLD` 중 계산시간·주기 누락과 I²C 출력 갱신을 함께 확인해야 한다.

1000→500 Hz는 같은 PID 계산의 초당 실행 횟수를 절반으로 줄인다. 20 kHz 엔코더 인터럽트와 같은 빈도의 UART 작업은 그대로이므로 전체 부하가 절반으로 감소하는 것은 아니다. 현재 I²C 출력 스케줄러도 제어 tick에 연결되어 있어 출력 주기 영향을 함께 확인해야 한다. 절감량은 활성 구동 중 측정한다.

현재 보정은 1ms 시간 단위를 전제로 한다. 500 Hz 비교를 진행하려면 PID 적분·미분 계수의 이산화, 속도 필터, 정지 판정, fault 시간 계산을 함께 수정하고 재보정해야 한다. 타이머 값만 바꾸지 않는다. 현재 기록에는 제어 주기 누락이 없어, 우선 검증된 1000 Hz를 유지한다.

다음 검증은 ROS 어댑터 연결 후 센서·SLAM·Nav2를 동시에 실행하며 명령 간격, 수신 데이터 나이, MCU 제어 누락, 통신 오류를 기록하는 것이다. 지면 주행의 속도 오차·정지 거리·방향 변화도 확인한다. 평균 부하만으로 통과 판정하지 않으며 오래된 명령과 통신 중단에서 정지되는지 검증한다. 바퀴 반지름·윤거 실측 후 ROS의 m/s 및 rad/s 한도를 정한다.
